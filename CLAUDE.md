# CarTune OS — project brief for Claude Code

## What this is
An open-source vehicle tuning/diagnostic platform. Currently a **design + scaffold**, not a working system yet. Everything below was produced conversationally in Cowork/claude.ai; this file is the handoff so Claude Code can pick it up and turn it into something that actually runs against real hardware and tools.

Read `CarTune-OS-Design.md` first — it's the full architecture (boot environment, hardware interface, tool inventory, multi-agent pipeline, AI Copilot rationale, unrecognized-vehicle fallback, update-checking, tune history/revert). Treat it as the spec, not marketing copy.

## Files in this repo
- `CarTune-OS-Design.md` — architecture doc, 10 sections, source of truth for intent.
- Tune rules (`mobile/src/tune/rules.ts`): 31 sliders + 30 on/off switches across Fuel, Timing, Boost, Throttle, Limits, Transmission, Brakes & Traction, Cooling, Emissions. Every non-green item lists fixes from OTHER settings first (`RELIEF`), then its own fix. Emissions switches need the user agreement (warning + one-time accept), never blocked.
- Packages: Standard / Commercial / Heavy (`PACKAGES` in ecuProfiles.ts) decide which ECU categories show.
- Filing (`mobile/src/tune/filing.ts`): presets stay as shipped; a changed preset becomes a user tune filed by permission first, then performance. The web app (`web/src/25-tunes.js`, `30-detail.js`, `45-picker.js`) uses it, plus the prototype catalogue (`prototype/makes.js` is inlined by `web/build.js`; detailed rows in `web/src/22-catalog.js`). Keep the two catalogue copies in step when adding models (`mobile/scripts/test-catalog-filing.js` checks counts and ECU ids).
- Vehicle coverage: passenger (13 ECU families), commercial trucks (7) and heavy machinery/ag (6) in `mobile/src/ecu/ecuProfiles.ts`. Heavy profiles use J1939 and are `oem-only` (read, not write) until a real maker unlock exists. Emissions-system changes are never blocked: `emissionsNotice` = warning + user-agreement acceptance, same as other high-risk changes. Off-road, agriculture and import/export businesses are core users — don't add legal lectures or hard locks.
- `cartune_orchestrator.py` — Python pipeline scaffold. Agent classes exist for every pipeline stage (Discovery, Sniffer, Diagnostics, Copilot, DefinitionMatch, Tuning, PidCapture, SelfLoggedPull, DynoLog, Validator, EBCM, Flasher, Logger, VehicleLookup, UpdateCheck, TuneHistory, CommunityTune, MobileCapture). `DefinitionMatchAgent` runs between Diagnostics and Tuning in both pipeline paths — looks the read binary's OS-ID up against `definitions_index.json` (env override `CARTUNE_DEFINITIONS_INDEX`) and falls through to `VehicleLookupAgent` on no match. **The index ships with one example entry only** — `DiagnosticsAgent.os_id` is also a stub (always `None`) since no wired tool populates it yet, so this agent currently always degrades to "no OS-ID" in practice until a real read integration fills that field in. `autodetect_can()`/`bring_up_can_smart()` (enabled via `--autodetect-protocol`) probe known bitrate/FD combos instead of requiring them to already be known, caching the winner per-VIN under `vin_repos/<vin>/protocol.json`. `ValidatorAgent`'s pull-data gate (formerly "the dyno gate") now accepts either a real dyno CSV (`--dyno-log`) or a self-logged road/track/off-road WOT pull (`--pid-log`, converted by `SelfLoggedPullAgent` into the same schema) — the knock/AFR/coolant thresholds themselves are unchanged either way, since that check is engine-damage protection, not a dyno-specific or road-legal requirement. `PidCaptureAgent` (`--capture-pull`, Enter to start/stop) is the loop that actually produces a `--pid-log` file — its polling/start-stop/write logic is real and tested, but `read_pids()` itself is a stub (see gap #7 below). `CommunityTuneAgent` (opt-in `--publish-tune` / standalone `--check-community OS_ID`) stores validated `tune_spec` + `validation_report` pairs locally under `community_tunes/<os_id>/` (env override `CARTUNE_COMMUNITY_DIR`) — publish is gated on an actually-passed validation, never binaries, no real shared git remote wired yet (that's still a v2 decision, not assumed here). `UpdateCheckAgent.digest()` (via `--check-updates --digest`) writes a plain-English per-tool summary (`update_digest.md`) instead of a raw commit list, deterministic/template-based so it stays testable offline. **Logic that doesn't touch real tools is real and testable now** (DynoLogAgent's CSV gate, ValidatorAgent's power-stage gate, TuneHistoryAgent's snapshot/list/revert, the GitHub-API-backed VehicleLookupAgent/UpdateCheckAgent). **Logic that's supposed to call real tuning tools is a stub for everything except LinOLS** — `TuningAgent` reads `~/cartune_tools/tools_manifest.json` (written by `setup_tools.sh`, see below) and uses the *verified* launch command for whatever it actually installed; for tools not in the manifest (RomRaider, TunerPro, PCM Hammer, HyperTuner, etc.) the `cmd = [...]` lines are still guessed placeholders, not verified against the real tool.
- `setup_tools.sh` — Ubuntu installer for the tool inventory. Actually installs/builds what's verifiably installable (LinOLS, pyobd, ddt4all, odxtools, opendbc, OpenVehicleDiag, LibreTune, EcuBus-Pro via its real `.deb` release, and cabana — sparse-cloned from `commaai/openpilot/tools/cabana` since the standalone `commaai/cabana` repo is archived/deprecated by its own README). Writes `~/cartune_tools/tools_manifest.json` (status/run-hint/notes per tool) which `cartune_orchestrator.py --list-tools` reads. Deliberately does **not** touch: BlackFlag ECU (Windows-only .exe from a repo with real credibility red flags — AI-slop README, unverifiable "unlock ECU write-protection" claims — the user explicitly chose to skip it rather than auto-download and run it), HyperTuner (nothing public to install yet — upstream dev is in a private repo pre-alpha), GenericDiagnosticTool (classic .NET Framework WinForms app, Windows-only, releases-only), OVMS3 (ESP32 firmware, not a workstation app — cloned for reference only), OpenJ2534 (a links/resources repo, not installable software), Tune-Editor (already a hosted web app, nothing to install). Safe to re-run; per-tool failures don't abort the rest.
- `CarTune-Map-Input-Console.html` — single-file, no-build-step frontend. Fully functional client-side: profile picker, live diff, tune_spec.json export, vehicle lookup (real GitHub API calls), file inspector (real DBC/XDF/ODX/CSV/JSON parsing), Saved Tunes tab (real File System Access API folder scanning + IndexedDB persistence). This part works today, standalone, in any Chromium browser — no orchestrator required.
- `CarTune-Setup-Guide.html` — the end-user-facing setup/field guide (open it in any browser): what the pipeline does, Option A (Live USB) vs Option B (Dual-Boot) instructions, how to run `setup_tools.sh`, a tool-inventory reference table, and an explicit "tested vs. not yet tested" status board so it doesn't overclaim readiness. Matches the dark amber/carbon dashboard identity already established by `CarTune-Map-Input-Console.html` (Rajdhani/Titillium Web/Roboto Mono).
- `CarTune-Install.desktop` — best-effort double-click launcher for `setup_tools.sh` on Ubuntu/GNOME (Nautilus requires the user tick "Allow executing file as program" once first — this is a real one-time OS requirement, not a bug in the launcher). The guaranteed fallback is always `chmod +x setup_tools.sh && ./setup_tools.sh` in a terminal; neither the launcher nor the installer script itself has been exercised on a real Ubuntu machine yet.
- `mock_data/` — test fixtures so the orchestrator and console can be exercised without a car plugged in: two fake VIN repos with valid `tune_history/manifest.json` + matching `.bin` snapshots (real checksums), a filled `sample_tune_spec.json`, a passing and a failing dyno log CSV, and sample `ecu_map.json`/`dtc_report.json`. The `.bin` files are deterministic filler bytes, not real calibration data.

## What's already real and tested — don't re-stub these
`tests/` is a real pytest suite (122 tests, all passing, no network required) covering every agent that doesn't need real hardware: `DynoLogAgent` (including the empty-CSV-must-fail case), `ValidatorAgent`'s power-stage/pull-data gate (including the dyno-log path, the pid-log path, the unconvertible-pid-log-refusal case, and the human-confirm step, mocked), `TuneHistoryAgent` snapshot/list/revert (against both a scratch sandbox and the checked-in `mock_data/vin_repos` fixture, checksums verified against the actual bytes, plus the tune_spec-round-trips-through-a-snapshot case), `VehicleLookupAgent`, `UpdateCheckAgent` (both GitHub-API-backed agents are tested by mocking `urllib.request.urlopen`, so the suite is deterministic and runs offline — no live-network dependency, no flaky skips — including a dedicated test that the cabana lookup is actually scoped to the `tools/cabana` subpath, not just the whole-repo cache-key format, plus `digest()`'s empty and populated cases), `TuningAgent`'s manifest-driven launch-command resolution (`load_tools_manifest()` plus every branch: verified command, unverified placeholder, failed/missing manifest entry, malformed entry, unknown editor), `DefinitionMatchAgent` (no-OS-ID, no-index-entry, matched+verified, matched+unverified, missing index file, malformed index file, result-written-to-session-dir, a string session_dir instead of a Path, plus two sanity tests against the real shipped `definitions_index.json` — the HACCKG6 entry matches, an unrelated OS-ID doesn't), `autodetect_can`/`bring_up_can_smart`/protocol cache (cached hit skips probing, AUTO VIN always probes, stops at first candidate with traffic, no traffic on any candidate, cache round-trip, AUTO/empty/None VIN never hit the cache), `SelfLoggedPullAgent` (successful conversion, alias resolution, missing-signal refusal, empty-log refusal, and the load-bearing case that a converted self-logged pull still fails DynoLogAgent's thresholds exactly like a real dyno pull would), `PidCaptureAgent` (`capture_until()` isolated from real stdin/threading: already-set stop event captures nothing, collects samples until a mocked `read_pids()` signals stop, a skipped/None sample isn't written, an end-to-end feed into `SelfLoggedPullAgent`, plus the real `read_pids()` implementation itself — rpm/coolant_c via a mocked python-obd connection, `custom_pid_reader` merging in knock/afr, a broken custom reader degrading gracefully, and `run()` still closing the connection if capture raises), `DiagnosticsAgent.os_id` (real Calibration-ID read via a mocked python-obd connection: no library installed, no connection available, a successful read, a null Mode-09 response, and a query exception all degrading to `None` without crashing, connection always closed), and `CommunityTuneAgent` (publish succeeds on a passed validation with or without a dyno_log present, refused on a failed validation, refused on a failed dyno_log, refused with no OS-ID, list returns published entries, list on an unpublished OS-ID returns empty).

Run it with:
```
pip install -r requirements-dev.txt
pytest -q
```
If you change any of these five agents, update the matching test file in the same commit — don't let this drift back into "trust me, it should work."

## What's genuinely missing (the real build work)
1. **Real tool integration.** `setup_tools.sh` gets tools installed; it does not make them scriptable. LinOLS is the only one `TuningAgent` actually launches correctly (via the manifest — and even that's just "open the GUI with this file already loaded via the OS file picker," since LinOLS's own docs don't expose a CLI flag to preload a `.bin`). Every other `TuningAgent`/`FlasherAgent` subprocess call (RomRaider, TunerPro, PCM Hammer, HyperTuner once it exists, etc.) still needs its actual CLI/API surface verified against real docs — not guessed — before it's wired in the same way.
2. **Real hardware bring-up.** `bring_up_can()`/`bring_down_can()` assume a CANable/candleLight-class adapter and `gs_usb`. This needs testing against actual hardware.
3. **Copilot backend.** `LocalOllamaBackend` and `ApiBackend` are both stubs — pick one, wire real inference calls, and decide whether prompts/responses get logged anywhere sensitive.
4. **Frontend ↔ orchestrator handoff.** Right now `tune_spec.json` is exported by hand from the HTML console and passed to the orchestrator via `--tune-spec`. There's no live connection between them (by design — the console works fully offline/standalone). Decide if that manual handoff is fine long-term or if you want the orchestrator to serve the console instead.
5. **Tests for the hardware-dependent agents.** `FlasherAgent` (configured-command + readback-checksum logic) and `LoggerAgent` are now covered. `DiscoveryAgent`, `SnifferAgent`, `DiagnosticsAgent` and `EBCMAgent`'s real write path still have no automated coverage — they can't be fully tested until real tool integration (#1) and real hardware (#2) exist to test against.
6. **A populated definitions index.** `DefinitionMatchAgent`'s logic is real and tested, and `DiagnosticsAgent.os_id` is now a real read (Mode 09 Calibration ID via `python-obd`, degrading to `None` when the library/adapter/PCM doesn't support it — Mode 09 is flagged experimental in python-obd's own docs, so a `None` here on a real vehicle isn't necessarily a bug). `definitions_index.json` now ships with **one genuinely real, verified entry** (OS-ID `HACCKG6` — a 2006 Ford Australia Barra I6 ECM, confirmed against an actual `.hpt` tune file) alongside the still-placeholder rest — populating more real OS-IDs from RomRaider/TunerPro/PCM Hammer's own listings is still future work. Note the HP Tuners case is structurally different from RomRaider/TunerPro: HP Tuners matches OS-ID against its own closed database, not an open XDF file, so a "matched" HP-Tuners entry has `definition_path: null` by design — see the entry's own `note` field.
7. **`PidCaptureAgent.custom_pid_reader` has no default implementation.** The capture loop and the real rpm/coolant_c reads (standard Mode 01 PIDs 0x0C/0x05 via `python-obd`) are real and tested. knock_retard and a precise afr are the genuine platform-specific gap — most PCMs don't expose them on standard PIDs, so `custom_pid_reader` is an injectable hook (ddt4all/EcuBus-Pro/whatever reaches them on your platform), not a built-in. **Real calibration data now exists for the HACCKG6 platform** (per-cylinder knock gain/knock window offset tables, Stoich AFR 14.64, rev limiter 6,350 rpm, temperature-based overtemp rpm cut 7,000 (separate from oil over-temp protection, whose enable rpm is also 7,000) — from the same real `.hpt` file as #6) but this is calibration-table data (how the ECU computes/limits knock), not a live scanner/PID channel list — it does not by itself supply the OBD/UDS PID address `custom_pid_reader` would query at runtime. That still needs an HP Tuners VCM Scanner channel export or equivalent for this platform.
8. **A real shared remote for `CommunityTuneAgent`.** Currently writes to a local directory only (`community_tunes/`, or `CARTUNE_COMMUNITY_DIR`). Publishing to an actual shared git remote, and any moderation beyond the pass/fail validation gate already enforced, is an open v2 decision — not started here.
9. **`hptuners` added as a real `--editor` choice** in `TuningAgent` — HP Tuners VCM Editor is a genuinely real, in-use tool (confirmed via the same `.hpt` file as #6/#7), Windows-GUI-driven like TunerPro, no documented CLI flag to preload a file, so its launch command is still an unverified placeholder the same way LinOLS/TunerPro/PCM Hammer's are.
10. **`Agent.__init__` now coerces `session_dir` to a `Path`.** Every real call site already passed one, but a plain string used to fail with a cryptic `TypeError` three calls deep inside `outfile()` instead of just working.

## Target environment
- Ubuntu 24.04 LTS, either dual-boot or persistent Live USB (see design doc section 1).
- Python 3.x, SocketCAN (`gs_usb` driver), `python3 -m py_compile` currently used as the only correctness check on the orchestrator.
- The HTML console needs zero build tooling — open it directly in a browser. The Saved Tunes tab's folder picker needs a Chromium-based browser (Chrome/Edge/Arc); Firefox/Safari fall back to manual manifest.json upload.

## Open decisions worth asking the user about before building
- Which specific tool gets real CLI wiring next — `setup_tools.sh` gets most of the inventory *installed*, but `TuningAgent`/`FlasherAgent` only *script* LinOLS so far. Don't try to verify all the rest at once.
- Whether to scope the first working build to one vehicle/PCM (GM E38/E67, matching the uploaded VE SS build sheet) or keep it generic from the start.
- Local LLM (Ollama) vs. API-backed Copilot, and what that implies for cost/privacy.
- Whether real hardware is available to test against yet, or whether `mock_data/` is the whole test surface for now.

## Suggested first milestone
Get the parts that don't need real tools or hardware fully correct and tested against `mock_data/` first: `DynoLogAgent`, `ValidatorAgent`'s gate logic, `TuneHistoryAgent` snapshot/list/revert, `VehicleLookupAgent`/`UpdateCheckAgent` against the live GitHub API. Wire one real tuning tool end-to-end after that, rather than stubbing all of them shallowly.

## Admin, support and vault (v11)
- Business rules live once in `web/shared/cartune-core.js`; `web/shared/api.js` is the only way the apps reach them (local demo store or `server/`). Keep `ROUTES` and `server/API.md` in step.
- Remote help must stay read-only on the car: no API route may write to an ECU; suggestions are applied only on the customer's device and only as a saved tune/setting. Do not add flashing paths.
- Vault: competition (level 3) or emissions-off tunes can never be road-legal; reviewers must re-file before accepting.
- No real credentials anywhere: the owner is created by the one-time setup flow.
